The `init` command is your starting point for every Tack Harness project space. It accepts any mix of Git URLs, local repo paths, project descriptions, business documents, or service-mapping data, automatically classifies each input, and writes structured knowledge to `wiki/` and the `AGENTS.md` project-info block. Running `init` a second (or third) time with new material only appends and merges — it never overwrites content you have already confirmed.

## Command Signature

```bash
/tack init [content]
# Aliases:
/tack i              # short form
/tack 初始化         # Chinese trigger
/tack init project   # natural language
/tack connect repo   # natural language
/tack organize docs  # natural language
```

## Parameters

<ParamField path="content" type="string" optional>
  Any combination of: a Git remote URL (`git@…` or `https://….git`), a local path containing `.git`, a free-form project description, pasted business documents or PRD text, or a service-to-repository mapping. Multiple types may be supplied at once; `init` processes each independently.
</ParamField>

## Prerequisites

<Note>
  The Tack skeleton (`AGENTS.md`, `harness/`, `wiki/`, `space/`) must already exist under `$root`. This is handled automatically when the skill is installed via `init-tack.sh`, which also ensures Git is available and initialises `$root` as a Git repository.
</Note>

## What It Does

`init` first inspects its input and routes each piece to the correct handling step. If no input is provided, it walks through steps 2 → 5 interactively.

### Input Auto-Classification

| Input Characteristic | Detected Type | Action |
|---|---|---|
| Starts with `git@`, `http(s)://…git`, ends with `.git` | Remote Git repo | Step 4 — remote clone branch |
| Local absolute/relative path with a `.git` directory | Local Git repo | Step 4 — local symlink branch |
| Sentence or multi-paragraph description of a project | Project information | Step 2 |
| PRD, design doc, architecture description, team landing doc | Business knowledge | Step 3 |
| Lines containing service name + repository mapping | Service↔repo mapping | Step 5 |
| Unrecognised or empty | — | Interactive steps 1 → 5 |

<Steps>
  <Step title="Ensure Project-Info Block">
    Runs `sh $root/harness/script/project.sh ensure $root` — a no-op if the block already exists, otherwise appends an empty template to `AGENTS.md`.
  </Step>
  <Step title="Collect Project Information">
    Extracts a project name (English kebab-case slug), 3–8 keywords, and a one-sentence description from user input. Confirms the result before writing via `project.sh set` and `project.sh keywords`.
  </Step>
  <Step title="Collect Business Documents">
    Accepts pasted text, document links, or oral descriptions (business scope, target users, team landing docs, PRDs). Content is classified and formatted only — never rewritten or fabricated.
  </Step>
  <Step title="Register Code Repositories">
    For **remote repos** runs `repo.sh clone $root <url…>`. For **local repos** runs `repo.sh link $root <path…>`. For a **scan directory** runs `repo.sh scan $root <dir>` (depth ≤ 5), lists discovered repos, and links the ones the user confirms. Multiple methods may be combined.
  </Step>
  <Step title="Build Service-to-Repo Mapping">
    For each registered repository, confirms the service name, responsible repo, and a one-line responsibility description. Persists each mapping via `project.sh service-repo`. Responsibilities and other non-code facts go into `wiki/manifest.md` in step 6, not into the YAML block.
  </Step>
  <Step title="Materialise Wiki Files">
    Writes wiki files from `harness/template/` only when the corresponding facts exist. Files are appended or merged if already present — never recreated from scratch.

    | File | Template | Condition |
    |---|---|---|
    | `wiki/manifest.md` | `wiki-manifest.md` | ≥ 1 repo registered |
    | `wiki/code-understanding.md` | `wiki-code-understanding.md` | ≥ 1 repo registered |
    | `wiki/business-understanding.md` | `wiki-business-understanding.md` | Any business material provided |
    | `wiki/decisions.md` | `wiki-decisions.md` | Historical ADR/conventions explicitly provided |
  </Step>
  <Step title="Ask User to Complete Gaps">
    On first initialisation, lists every "pending" item (service responsibilities, environment facts, middleware details) and invites the user to fill them in now. On subsequent calls only new material is merged.
  </Step>
  <Step title="Auto-Commit">
    Runs `space.sh commit $root "chore(tack): init global context"` — skipped automatically if there are no changes. The user never needs to touch Git for space-level changes.
  </Step>
</Steps>

## Outputs

<CardGroup cols={2}>
  <Card title="AGENTS.md (project block)" icon="file-lines">
    `name`, `description`, `keywords`, `root_path`, and `service_repo_mapping` fields written via `project.sh` scripts — no manual YAML editing required.
  </Card>
  <Card title="wiki/manifest.md" icon="map">
    Service overview table and per-service detail sections, rendered from the `service_repo_mapping` block. Environment and account facts are recorded here (never credentials).
  </Card>
  <Card title="wiki/code-understanding.md" icon="code">
    Repository overview table with real rows. Term→code and interface→scenario mapping tables are left empty for `ask` and `record` to populate later.
  </Card>
  <Card title="wiki/business-understanding.md" icon="book">
    Generated only when business material is provided. Contains business-line overview, background, concept glossary, and original user text preserved verbatim.
  </Card>
</CardGroup>

<Warning>
  `wiki/` files must contain only facts you have explicitly provided. Tack Harness will never fabricate technical stack details, business rules, call chains, or any other content you have not supplied. Credentials (passwords, tokens, keys) must never be written to wiki files — record only the retrieval method.
</Warning>

## Post-Completion Checklist

```
- [ ] $root is a Git repository (git -C "$root" status runs successfully)
- [ ] Every entry under $root/repo/ can be entered and git status executed
- [ ] AGENTS.md project block has name, keywords, and description filled in
- [ ] service_repo_mapping records all registered repos and has been reviewed by the user
- [ ] wiki/manifest.md and wiki/code-understanding.md exist with real repo rows (when repos are registered)
- [ ] wiki/business-understanding.md exists when business material was provided
- [ ] wiki/decisions.md exists with source annotations only when ADR/convention material was explicitly provided
- [ ] All user-supplied raw text is preserved verbatim in wiki/
- [ ] wiki/ contains only non-code facts, navigation anchors, business background, and sourced decisions — no code logic, call chains, or credential plaintext
- [ ] On first init, the "pending items" list was surfaced and the user was invited to complete it
- [ ] Nothing outside the AGENTS.md project-info block was modified
```
